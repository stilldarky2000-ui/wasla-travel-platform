# Booking conversations: implementation and deployment

## Scope

The shared Booking conversations inbox appears in Operations > Chat and Owner > Copilot. It keeps the existing palette and executive Copilot. New customer messages and internal notes are separate server-owned Firestore subcollections. Legacy chats remain a read-only archive; they are not automatically reclassified or exposed to guests. Existing dispatch templates are retained. Owner legacy chat replies and Operations complaint chat replies direct their drafts to the new booking inbox for review and explicit sending. Legacy email/newsletter tools remain unchanged and are not an inbound email integration.

Each booking can have one conversation. Staff can claim it and set Needs team reply, Waiting for guest, or Closed. A guest message reopens it. Notes do not change its public-message status. Public replies switch it to Waiting for guest. Staff identity comes from the verified Firebase user, never the submitted message. Notes and status/assignment events stay staff-only. A message saved in the conversation is distinct from an email provider accepting its notification; neither proves the recipient read it.

The guest page uses `/?conversation=BOOKING_ID#conversationToken=...`. The signed capability is booking-scoped, purpose-separated from voucher tokens, and expires after 30 days. Possession grants access: share it only with the guest. Staff can generate a fresh link. Rotating VOUCHER_LINK_SECRET invalidates all conversation AND existing voucher links. Per-link revocation is not yet implemented. Cancelled bookings can still contact support. No attachments, read receipts, inbound email sync, or WhatsApp sync are implemented by this change.

Messages are individual append-only documents, with server timestamps, retry request IDs, and paginated history. The API returns 50 messages per page without deleting older messages. The UI polls every 15 seconds while open. Internal notes and employee identities are excluded from guest API responses. Reply assistant receives only public conversation messages and the guest-facing booking allowlist. It drafts into the editor, never sends or changes bookings. GEMINI_API_KEY is optional for manual replies.

## Production requirements — do not skip

1. Confirm the Cloud Run Express server and all Functions use the same FIREBASE_PROJECT_ID and FIRESTORE_DATABASE_ID. Firebase static hosting alone does not serve `/api`; the application must reach the Express backend as in the existing Cloud Run setup. Retain the existing backend routing.
2. Cloud Run's service identity previously needed booking reads. It now also needs query/read/write access to `conversations` and its messages/notes (including atomic commits). Give the service identity the required Firestore data permissions with least privilege for this deployment; do not expose service-account keys to the browser. Browser rules intentionally deny all direct access to conversations, including staff browser SDK access.
3. Configure the SAME stable VOUCHER_LINK_SECRET (at least 32 bytes) in Cloud Run and Functions. Functions needs APP_URL set to the public HTTPS site, RESEND_API_KEY, RESEND_FROM_EMAIL using the verified sender, and OWNER_ALERT_EMAIL or the correct public settings support email. Resend DNS already configured elsewhere does not automatically inject credentials into a new Function. Explicitly bind runtime secrets to `notifyBookingConversation` and the existing notification Functions if your deployment uses Secret Manager. This source consumes environment variables; it does not create/bind secrets or alter DNS.
4. Deploy the new Firestore rules to the correct named database. Deploy the updated server/client, updated onBookingConfirmed/delivery Functions, and the NEW `notifyBookingConversation` Function. Do not release only the client or only the email link template. Schedule a coordinated staging rollout first.
5. Initial booking and confirmation emails now contain a private conversation link. Confirmation keeps its private voucher link as well. Already-confirmed booking creation is treated as a confirmation notification rather than an obsolete pending notification.
6. Guest public messages notify the owner by email. Staff public replies notify the guest. Internal notes do not send mail. The Firestore-created-message trigger retries failures independently from saving the message. Resend gets a stable idempotency key. `emailStatus` is `provider_accepted`, `retry`, or `blocked_missing_recipient`; privileged operators can inspect it in Firestore. Notifications contain a link, not the message body. Email replies still go to the support mailbox and do not enter this inbox automatically; the notification instructs the recipient to reply through the conversation link.
7. Monitor failed/retrying `notifyBookingConversation` invocations and messages missing `emailAcceptedAt`. Event retry retention is finite: reconcile unresolved notifications operationally; this change does not add a permanent scheduled mail-recovery sweep or guarantee exactly-once delivery. SMTP/provider checkpoint crashes can duplicate notifications. Fix recipient/configuration failures and replay unresolved events deliberately.
8. In staging, use two real staff accounts and one guest link. Test send/receive, concurrent replies, note isolation, assignment, expired/wrong-booking links, mobile layout, unavailable AI, provider failure/recovery, and real Resend inbox delivery. Confirm the booking receipt and voucher are still correct. Mocked local tests do not validate deployed IAM, Eventarc, Secrets, DNS, real staff tokens, or actual inbox arrival.

## Validation commands

- `npm test`: Functions build plus existing notification/voucher tests and conversation capability/provider tests. No real messages are sent.
- `npm run lint`: TypeScript check.
- `npm run build`: production client/PWA build.
- `npm run test:conversations:emulator`: requires Firebase CLI, Java, and local emulator; refuses a non-local emulator. Exercises real Firestore REST reads/atomic writes via an Express test server, concurrent messages, idempotency, privacy, assignment, pagination beyond 50, and denied browser reads/writes. Its staff middleware is a test stub; deployed Firebase role verification must be checked separately.

No production deployment, credentials change, or real notification send is performed by this patch. Existing legacy records are retained, not migrated or deleted. Data older than any historical truncation cannot be recovered by changing the new storage model.
